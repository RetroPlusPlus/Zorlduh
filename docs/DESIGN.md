# Zorlduh — design context

Authored at inception, 2026-11-10. What the project is, what is decided, and what stays true however the
implementation changes.

## What it is

Two things, in this order of priority for now:

1. **The start of an ecosystem library for Polyrhythm.** The engine is deliberately low-level: a set of
   primitives that compose orthogonally. This project grows the layer above them — reusable,
   distributable components that compose the primitives into higher-level features and lower the skill
   floor for making a game on the engine, the way the libraries around React make React easier to use.
   It starts from the components that the engine's existing component-style consumers each wrote for
   themselves. Packaging the components as separate modules comes later; every system written now is
   written so it can be lifted out whole.
2. **A top-down action-adventure game**, in the tradition of the genre's classic 2D entries: rooms
   explored on foot, a sword, hearts, enemies, items, dungeons. The game is the proving ground that
   decides what the library needs. For now it is a **technical template** — the systems any game of this
   kind needs — with no game-specific design yet. The game's own design opens when the template is done.

**Name:** Zorlduh. Executable, CMake prefix and C++ namespace `zorlduh`. Engine identity: organization
`Retro++`, application `Zorlduh`.

## Visual direction

- **Game Boy Color idiom:** viewport 160×144, 8×8 tile cells, 4-color palettes, 16×16 characters built
  from four cells, window scale 4.
- **Timing: a clean 60 Hz tick**, not the Game Boy's 59.73 Hz — `TickPeriodNs::Hz60` with no CPU model.
  Every duration in the game is counted in ticks, so a tick is 1/60 s.
- **Placeholder art** until real art replaces it: generated by a script, deterministic, committed. It
  makes behavior visible; it does not set a look.
- **Color is indexed (CLUT).** A sheet holds palette indices and no color; color comes from a
  palette image chosen per tile or sprite when it is drawn. Sheets are grayscale at the depth their
  indices need (2-bit for four colors), so each one reads by eye as its art. Maps are grayscale too,
  their ids spread across the range so a map reads by eye.
- **Assets are laid out by kind, then category:** `assets/gfx/`, `assets/palettes/`, `assets/maps/`
  (later `assets/audio/`), each with folders such as `tiles/`, `sprites/` and `hud/`. Every asset is baked
  into the executable.

## Tone and writing voice

None yet. The template has no text, story or characters. Decided when the game's own design opens.

## Mechanical identity

The template's verbs and systems:

- **Screen:** a 16 px HUD strip across the top; a 160×128 play area (20×16 cells) beneath it.
- **Rooms — free-form**, in the A-Link-to-the-Past model rather than one room per screen: a room is any
  rectangle of the world map, in cells, and rooms differ in size. The camera centers on the player and
  stops at the room's edges, so nothing outside the room is ever on screen. A room smaller than the play
  area is allowed and sits centered, with nothing drawn around it. Leaving a room through an opening in
  its edge scrolls to the room on the other side. Sizes are any number of cells, not multiples of a
  screen.
- **Player:** eight-direction walking — each held axis moves the player, so diagonals cover both at
  once; tile collision resolved per axis, so a diagonal into a wall slides along it; four facings, which
  a diagonal keeps when it already points along one of its two directions; walk animation.
- **Actors:** stable ids minted at spawn, per-room spawn tables, one wandering enemy kind.
- **Combat:** a sword swing with a hitbox ahead of the player, enemy knockback and death, player damage
  with knockback and invulnerability (shown by flicker), death and restart.
- **HUD:** hearts in half-heart steps; a heart pickup dropped by enemies.
- **Sound:** one cue per game event, played from the simulation's event stream.
- **Game states:** `Playing`, `Transition`, `GameOver`.

Terms used consistently: **room** (a rectangle of the world map), **play area** (the screen below the HUD
strip), **camera** (the world position shown at the play area's top-left), **actor** (anything spawned
in a room), **cell** (one 8×8 tile position).

## Hard constraints

- **Everything on screen is a component**: a stateless function, named for the thing it is, that takes
  the state it shows as parameters and returns the engine primitives it is, re-derived from state every
  frame; the frame is the list of what the components return. Depth is which layer a thing is on, and
  a thing not shown is simply not returned — so the game holds no CPU-side screen or tile map, no object
  buffer, no per-cell visibility or priority flag, no hide call, and no save-and-restore of screen
  contents.
- **The simulation has no draw types.** `src/game/` includes nothing from the engine's draw state or
  renderer and nothing from `src/render/`. Everything that changes over time advances in the tick;
  rendering only reads.
- **The simulation names what happened** as events; presentation and audio consume them.
- **Every system can be lifted out** into a standalone module: nothing under `modules/` includes a
  project header, and a system meant to be general holds no game constants.
- **The engine is consumed, not modified.** `engine/` is a pinned submodule; what the engine should do
  differently is raised with the engine project.
- **Original content only.** The game is in a genre and uses its mechanics; it recreates no existing
  game's names, characters, art, music, maps or dungeons.
- **Code-facing documentation** — module READMEs, guide pages, every source and build-file comment — is
  written in the present tense, says what the code does, and carries no development history.

## What must be preserved

- The component model of rendering above.
- The layer aggregates are this project's own, in `modules/layers/`, until the engine ships its own form.
  A layer built through them with no options draws exactly as a plain engine layer would: every layer
  field beyond its key, depth, size and content passes through with the engine's own default, and the
  layer's size is the active viewport.
- Library first: when a system could be general, it is written general and placed where it can be
  lifted out.
- The free-form room model and the camera behavior above.
- The Game Boy Color idiom at a 60 Hz tick.
